# 동기 vs 비동기 처리 결과·속도 비교

> 교재: `FastAPI_HuggingFace/Vision/02_FastAPI_ResNet18_Redis_Celery_동기비동기.md` 13절 비교 규칙
> 측정 스크립트: `tools/bench_sync_async.py` (교재 외 추가) · 원자료: `reports/sync_async_requests.csv`, `reports/sync_async_summary.json`, `reports/async_job_timing.csv`

## 측정 조건

| 항목 | 값 |
|---|---|
| 모델 | `microsoft/resnet-18` 원본 (ImageNet 1,000종, Fine-tuning 전) |
| 추론 장치 | CPU (`hf_model.py`의 `device=-1`, 교재 그대로) |
| 이미지 | 콩잎 Test 사진 10장 (3클래스를 번갈아 선택, 500×500 JPG) |
| 워밍업 | 서버·워커 각각 1회 요청 후 측정 (측정에서 제외) |
| 반복 | 같은 10장을 캐시 MISS 1회 → 캐시 HIT 1회, 동기·비동기 각각 |
| 캐시 | 매 묶음 전에 Redis 캐시 DB(`/1`)만 비움 |
| Worker | Celery `--pool=solo --concurrency=1` (한 번에 1개 처리) |
| 상태 확인 간격 | 측정 스크립트 0.05초 (브라우저 화면은 1초) |
| 환경 | WSL2 Ubuntu, Python 3.11, torch 2.15, transformers 4.57, Redis 7.4·PostgreSQL 17 (Docker) |

## 결과 1 — 처리 결과

**같은 사진 10장의 Top-1 라벨과 점수가 동기·비동기에서 10/10 같았다.** 같은 모델, 같은 `classify_with_cache()`를 쓰기 때문이다. 처리 방식은 결과가 아니라 **언제 받느냐**만 바꾼다.

원본 모델이라 라벨은 콩잎 병 이름이 아니라 ImageNet 이름이다. 콩잎 3종 분류는 Fine-tuning 후에야 가능하다.

## 결과 2 — 한 장씩 보낼 때 (중앙값, ms)

| 방식 | 캐시 | HTTP 응답 | 결과 받기까지 (스크립트) | 접수→완료 (DB 기록) | 모델 추론 |
|---|---|---:|---:|---:|---:|
| 동기 | MISS | 22.8 | 22.8 | — | 17.5 |
| 동기 | HIT | **1.5** | 1.5 | — | 없음 |
| 비동기 | MISS | **7.5** | 63.0 | 30.4 | 19.5 |
| 비동기 | HIT | 7.7 | 63.3 | 7.7 | 없음 |

읽는 법:

- **비동기의 HTTP 응답(7.5)은 "접수"까지의 시간이다.** 동기의 22.8은 "결과"까지의 시간이다. 둘을 나눠서 "비동기가 3배 빠르다"고 말하면 안 된다 (교재 13절)
- 비동기로 결과를 받기까지는 63ms로 **동기보다 오래 걸렸다.** 파일 저장, DB 기록, Redis 큐, Worker, 다시 DB 조회 단계가 더 있기 때문이다
- 스크립트의 63ms는 0.05초마다 확인한 값이라 **확인 간격만큼 늦게 잡힌다.** DB에 남은 접수→완료 시간(30.4ms)이 실제 처리 시간에 더 가깝다. 브라우저 화면(1초 간격)에서는 결과가 약 1초 뒤에 보인다
- 모델 추론 시간은 두 방식이 비슷했다(17.5 vs 19.5). **처리 방식이 AI 추론을 빠르게 하지는 않는다**
- 캐시 HIT이면 추론을 건너뛴다. 동기는 22.8 → 1.5ms, 비동기 Worker는 30.4 → 7.7ms

## 결과 3 — 10장을 한꺼번에 보낼 때 (ms)

| 방식 | 가장 늦은 HTTP 응답 | 10장 결과 모두 받기까지 |
|---|---:|---:|
| 동기 | 163.3 | **170.3** |
| 비동기 | 193.3 | 372.5 |

- 동기는 FastAPI가 요청마다 스레드를 써서 여러 장을 **동시에** 추론했다
- 비동기는 Worker가 1개(`solo`)라 **한 장씩 차례로** 처리했다. DB 기록에서 마지막 작업은 접수 후 330.7ms에 끝났다
- 이 조건(이미지 작음, 추론 20ms, Worker 1개)에서는 **비동기가 전체 처리량에서 더 느렸다**

## 결과 4 — 첫 요청

워밍업 요청에서 Worker의 첫 추론은 **3,388.6ms**였다 (DB `job_id=1`). 모델을 처음 메모리에 올리는 시간이 포함된다. 이후에는 약 19ms다. 서버도 첫 동기 요청에서 같은 일이 생긴다. **그래서 워밍업을 빼고 측정했다.**

## 결론

| 질문 | 답 |
|---|---|
| 결과가 다른가? | 아니다. 10/10 같다 |
| 어느 쪽이 빠른가? | **무엇을 재느냐에 따라 다르다.** 접수 응답은 비동기(7.5ms), 결과까지는 동기(22.8ms) |
| 비동기는 언제 유리한가? | 추론이 길어 HTTP를 오래 붙잡으면 안 될 때(타임아웃·화면 멈춤), 요청이 몰려 큐에 쌓아 두고 Worker를 늘려 나눠 처리할 때, 처리 상태(queued·running·done·failed)를 기록해야 할 때 |
| 이번 측정에서 동기가 나았던 이유 | 추론이 20ms로 짧고 Worker가 1개였다. 비동기 단계(DB·큐·조회)가 추론보다 오래 걸렸다 |
| 캐시 효과 | 같은 사진 반복이면 두 방식 모두 추론을 건너뛴다. 모델을 바꾸면 키가 바뀌어 섞이지 않는다 |

## 한계

- 원본 모델, CPU 추론으로 측정했다. Fine-tuning 모델이나 GPU, 더 큰 모델이면 숫자가 달라진다
- 10장 1회씩만 측정했다. 교재 권장(5~10회 반복)에 맞추려면 묶음을 반복해야 한다
- 비동기 "결과 받기까지"는 상태 확인 간격의 영향을 받는다
- Worker 수를 늘린 비교(`--concurrency` 증가)는 하지 않았다
- 이 숫자는 이 PC 한 대 기준이다
